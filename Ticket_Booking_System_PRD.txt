# Ticket Booking System — Product Requirements Document (PRD)

**Version:** 1.0  
**Status:** Implementation Ready  
**Product Type:** Web-based ticket booking platform  
**Primary Domains:** Movies and Concerts  
**User Roles:** Customer, Organiser, Admin

---

## 1. Product Overview

The Ticket Booking System is a web platform for discovering and booking movie and concert tickets through a visual seat-selection experience.

The system must support high-demand booking scenarios where multiple customers attempt to select the same seats simultaneously. It must temporarily hold selected seats, automatically release abandoned holds, prevent double booking, and provide a waitlist when an event or seat category is sold out.

After a successful booking, the customer receives a digital ticket containing a QR code encoding the booking reference.

The platform has three roles:

- **Customer:** Browses events, selects seats, books tickets, joins waitlists, views booking history, and cancels bookings.
- **Organiser:** Creates and manages movie/event listings and views booking and revenue information.
- **Admin:** Creates and manages venues, seat layouts, seat categories, and platform-level configuration.

The core requirements are based on the supplied project specification, including visual seat maps, configurable seat-hold TTL, concurrency protection, category-based waitlists, automatic seat offers, QR ticketing, email delivery, and organiser revenue summaries.

---

# 2. Problem Statement

Traditional ticket booking systems face several problems:

1. Popular events can sell out immediately.
2. Seats selected during checkout may remain unavailable when customers abandon payment.
3. Cancelled bookings may leave seats unused.
4. Multiple customers may attempt to reserve the same seat at the same time.
5. Customers need a clear real-time view of seat availability.
6. Customers waiting for sold-out events need an automated and fair allocation mechanism.
7. Confirmed bookings require a reliable digital ticket.

The product solves these problems through temporary seat holds, concurrency-safe booking, real-time seat status, waitlists, automated seat reassignment, and QR-based digital tickets.

Build a reliable and user-friendly ticket booking platform where customers can confidently select seats, complete bookings, and receive digital tickets while the platform efficiently handles high-demand events and cancelled-seat reallocation.

# 9. Seat State Model

Every seat for a show must have a current state.

## 9.1 States

### AVAILABLE

Seat can be selected.

### HELD

Seat is temporarily reserved by a customer during checkout.

A held seat must contain:

- Customer/user ID.
- Hold identifier.
- Hold creation time.
- Hold expiration time.

### BOOKED

Seat has been successfully booked.

### EXPIRED

A hold has expired and the seat must return to AVAILABLE.

### CANCELLED

A previously booked seat has been cancelled and becomes available for reallocation.

# 12. Seat Hold System

## 12.1 Purpose

The hold system prevents a customer from losing seats while completing checkout.

## 12.2 Default TTL

The system should support a configurable TTL.

Example:

**10 minutes**

The actual TTL must be configurable rather than hardcoded.

## 12.3 Hold Creation

When a customer selects seats:

1. Backend receives seat IDs.
2. Backend verifies that each seat belongs to the requested show.
3. Backend verifies that each seat is available.
4. Backend attempts an atomic hold operation.
5. If all requested seats can be held, the transaction succeeds.
6. If any requested seat cannot be held, the operation fails safely.
7. Held seats receive an expiration timestamp.

## 12.4 Partial Hold Rule

For a multi-seat request:

> Either all requested seats are successfully held or none are held.

This prevents partial reservations.

## 12.5 Hold Expiration

When TTL expires:

1. System identifies expired holds.
2. Held seats are released.
3. Seat status changes to AVAILABLE.
4. Real-time clients are informed of the update.

# 13. Concurrency Protection

Concurrency is a critical system requirement.

Two customers must never both successfully hold or book the same seat.

## 13.1 Required Behavior

If Customer A and Customer B attempt to hold Seat A1 simultaneously:

- Only one request succeeds.
- The other request receives a clear failure response.
- The losing customer sees the seat as unavailable.

## 13.2 Recommended Implementation

Use database transactions and row-level locking or an equivalent atomic mechanism.

Possible approaches:

- Database transaction with `SELECT ... FOR UPDATE`.
- Atomic conditional update.
- Unique constraints.
- Transaction isolation.
- Distributed locking if required by architecture.

The implementation must guarantee that concurrent requests cannot create two valid holds for the same show-seat combination.

The waitlist must maintain FIFO ordering.

- Waitlist ID.
- Event/show ID.
- Category ID.
- Customer ID.
- Queue position.
- Created timestamp.
- Status.

Possible statuses:

- WAITING
- OFFERED
- ACCEPTED
- EXPIRED
- REMOVED

---

# 23. Waitlist Assignment

When a booked seat becomes available:

1. System identifies the seat category.
2. System checks the category waitlist.
3. System selects the first eligible WAITING customer.
4. System creates a time-limited offer.
5. Customer receives notification.
6. Seat is temporarily associated with the offer.
7. Customer opens the offer link.
8. Customer completes booking within the allowed period.

---

# 24. Waitlist Offer TTL

The waitlist offer must have a configurable expiration period.

Example:

**5 minutes**

The offer should contain:

- Offer ID.
- Customer ID.
- Seat/show.
- Expiration timestamp.
- Secure token/link.
- Status.

---

# 25. Expired Waitlist Offer

If the customer does not complete the booking before the offer expires:

1. Offer becomes EXPIRED.
2. Seat becomes eligible for the next waitlisted customer.
3. Next customer receives an offer.
4. Process repeats until the seat is booked or no eligible waitlist entries remain.

---

# 26. Waitlist Fairness

The system must preserve queue ordering.

A later customer must not receive an offer before an earlier eligible customer unless the earlier customer:

- Rejects the offer.
- Lets it expire.
- Is otherwise ineligible.

# 42. Seat Hold Transaction

A recommended logical transaction:

```text
BEGIN TRANSACTION

Lock requested show-seat rows

Check all seats are AVAILABLE

If any seat is unavailable:
    ROLLBACK

Otherwise:
    Create Hold
    Create HoldItems
    Update seats to HELD
    Set expiresAt

COMMIT
```

This transaction must be atomic.

---

# 43. Booking Transaction

```text
BEGIN TRANSACTION

Lock hold

Verify hold belongs to current user

Verify hold has not expired

Verify seats are still held

Create Booking

Create BookingItems

Update seats:
    HELD → BOOKED

Mark Hold as COMPLETED

COMMIT
```

After commit:

- Generate/send ticket.
- Publish booking confirmation event.

---

# 44. Hold Expiration Worker

A background scheduler should periodically find expired holds.

Pseudo-flow:

```text
Find HELD records where expiresAt <= currentTime

For each expired hold:
    Start transaction
    Lock hold
    Re-check expiration/status
    Release associated seats
    Mark hold EXPIRED
    Commit

Publish seat availability update
```

The re-check is important because a customer may complete checkout while the scheduler is processing.

---

# 45. Waitlist Processing Worker

When a seat becomes available:

```text
Find next WAITING customer
Create WAITLIST OFFER
Set offer expiration
Notify customer
```

When an offer expires:

```text
Mark offer EXPIRED
Return seat to allocation pool
Find next WAITING customer
Create new offer
Notify next customer
```

2. User's hold expires while checkout is open.
3. User submits checkout exactly when TTL expires.
4. Scheduler processes an already-booked hold.
5. Customer refreshes checkout page.
6. Customer clicks booking confirmation multiple times.
7. Customer loses network connection during checkout.
8. Email service fails after booking succeeds.
9. QR generation fails after booking succeeds.
10. Customer tries to use an expired waitlist offer.
11. Two processes attempt to allocate the same cancelled seat.
12. Waitlist becomes empty.
13. Customer attempts to join the same waitlist multiple times.
14. Event is cancelled while seats are held.
15. Venue seat is removed after events have been created.
16. Organiser attempts to modify an event after bookings exist.
17. Customer attempts to cancel an already cancelled booking.
18. Hold-expiry worker runs multiple times for the same hold.

# 56. Business Rules

1. A seat belongs to a venue.
2. A show references a venue through its event.
3. Each show has independent seat inventory.
4. A seat can have only one active hold at a time.
5. A seat can have only one confirmed booking at a time for a specific show.
6. A hold expires automatically after its TTL.
7. A booking can only be created from a valid active hold.
8. Waitlists are maintained per show and seat category.
9. Waitlist offers have expiration times.
10. Expired offers move allocation to the next eligible customer.
11. Booking references are unique.
12. Customer booking history must only expose that customer's bookings.
13. Organisers can access only authorized event information.
14. Admins have venue and seat-layout management privileges.

# 68. Key Product Risks

## Risk 1 — Double Booking

**Impact:** Critical

**Mitigation:** Database transactions, row locking/atomic updates, constraints, and concurrency testing.

## Risk 2 — Stale Seat Map

**Impact:** High

**Mitigation:** WebSockets/realtime updates plus server-side validation.

## Risk 3 — Expired Holds Remaining Active

**Impact:** High

**Mitigation:** Background scheduler and database-level expiration checks.

## Risk 4 — Waitlist Race Conditions

**Impact:** Critical

**Mitigation:** Transactional allocation and locking around seat/offer assignment.

## Risk 5 — Email Failure

**Impact:** Medium

**Mitigation:** Store booking independently of email delivery and retry failed notifications.

# 69. Final Product Principle

The frontend may improve the user experience, but **the backend/database is the final authority for seat availability**.

Every critical operation must be validated server-side.

The three most important technical guarantees are:

1. **A seat cannot be successfully allocated to two customers for the same show.**
2. **Expired holds automatically return seats to the available pool.**
3. **Cancelled seats are automatically offered to waitlisted customers in queue order.**

These areas align directly with the evaluation focus in the supplied specification. fileciteturn0file0L48-L54
